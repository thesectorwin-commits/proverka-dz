# CLAUDE.md

Контекст для Claude Code при дальнейшей доработке этого проекта. Прочитай целиком перед тем, как что-то менять — здесь есть решения, которые выглядят как «упрощение», но на самом деле сознательные.

## Что это за проект

Сервис проверки домашних заданий школьников 1-5 класса (математика, русский, английский, окружающий мир) по фото тетради. Родитель или ребёнок фотографирует выполненное задание, сервис через Claude API находит ошибки и даёт подсказку, но **не даёт готовое решение** — цель, чтобы ребёнок сам исправил ошибку.

Это бэкенд-версия, выросшая из клиентского прототипа (одностраничный HTML-артефакт, который вызывал Anthropic API прямо из браузера). Вся логика проверки перенесена в `lib/claude.ts` почти без изменений — она уже была вылизана на реальных тестах с фотографиями детских тетрадей.

## Три принципа, которые нельзя нарушать при доработке

Это не пожелания — это принятые владельцем проекта решения, обсуждённые отдельно.

### 1. Фотографии не хранятся нигде, никогда — КРОМЕ одного явного исключения

В `app/api/checks/route.ts` фото читается в `Buffer`, кодируется в base64, уходит в Anthropic API, и переменная выходит из области видимости. Не логируй base64-содержимое фото.

**Единственное исключение (14.08.2026, осознанное решение владельца проекта):** фото решения (не фото учебника) сохраняется в приватный Supabase Storage бакет `check-photos` на **48 часов**, чтобы показывать превью в истории проверок — см. подробный раздел «Хранение фото решения (48 часов)» ниже. Это НЕ отменяет принцип по умолчанию — если в коде появляется НОВОЕ место, где что-то сохраняется на диск/в БД/в другое хранилище «на всякий случай», это по-прежнему нужно обсуждать с владельцем явно, а не считать уже решённым вопросом задним числом.

### 2. Из Яндекс ID берётся только `yandex_id`

В `app/api/auth/yandex/callback/route.ts` из ответа `login.yandex.ru/info` читается только поле `id`. Поля `login`, `default_email`, `real_name`, `default_avatar_id` в ответе присутствуют, но **сознательно игнорируются** — это не недоработка. Не добавляй их сохранение без явного запроса — это удвоит объём персональных данных в базе.

### 3. API-ключи и service_role — только на сервере

`ANTHROPIC_API_KEY` и `SUPABASE_SERVICE_ROLE_KEY` импортируются только в файлах внутри `app/api/**` или в `lib/*.ts`, которые импортируются оттуда. **Никогда** не импортируй `lib/supabaseServer.ts` или что-либо с этими ключами в файл с директивой `'use client'` — это моментально утечёт в браузерный бандл.

## Стек

- Next.js 14 (App Router) + TypeScript
- Supabase — сейчас как обычный Postgres + JS-клиент с `service_role`, **не используется Supabase Auth** (своя авторизация через Яндекс ID + JWT в cookie)
- Tailwind CSS
- `jose` — подпись/проверка JWT для сессий
- Claude API (`claude-sonnet-4-6`) для распознавания и проверки фото

## Почему НЕ Supabase Auth

Специально не использован Supabase Auth, потому что авторизация — через Яндекс ID, а не email/пароль или соцсети, которые поддерживает Supabase из коробки. Вместо этого — своя таблица `users` с `yandex_id` и сессии на подписанных JWT в httpOnly cookie (`lib/session.ts`). Если в будущем понадобится добавить вход по email — это отдельная таблица/логика, не переделывай существующую сессионную систему без необходимости.

## Схема базы данных

Полный SQL в `supabase/schema.sql`. Кратко:

- `users` — только `id`, `yandex_id`, `is_admin`. **Нет** email/имени/аватара.
- `children` — `label` (псевдоним, НЕ настоящее имя ребёнка), `grade`
- `checks` — одна проверка: предмет, оценка, общий комментарий, счётчик токенов, `photo_path` (см. «Хранение фото решения (48 часов)» ниже — единственное исключение из «нет ссылки на фото»)
- `check_tasks` — отдельные задания внутри проверки (то, что в прототипе было массивом `tasks` в JSON)
- `usage_counters` — лимит бесплатных проверок в месяц (сейчас 5, см. `FREE_CHECKS_PER_MONTH` в `app/api/checks/route.ts`)
- `subscriptions` — заготовка под платную подписку, **эндпоинтов оплаты ещё нет**

RLS включён на всех таблицах, политик для `anon`/`authenticated` **намеренно нет** — доступ только через `service_role` с сервера. Если Claude Code решит «добавить политику RLS для authenticated», сначала уточни у владельца — это может означать переход на Supabase Auth, которого сейчас нет.

## PWA и push-уведомления

Сайт — устанавливаемое PWA (иконка на главном экране телефона), без готовых
библиотек вроде `next-pwa` — service worker написан вручную
(`public/sw.js`), чтобы полностью контролировать, что кэшируется.

- **`public/manifest.json`** + иконки в `public/icons/` (сгенерированы
  программно, без внешнего графического редактора — просто закрашенный
  квадрат в цвет `--green-check` с галочкой).
- **`public/sw.js`** — кэширует только статику. `/api/**` **никогда** не
  кэшируется — это осознанное решение, чтобы не отдать устаревший или
  чужой результат проверки. Если понадобится расширить офлайн-режим,
  сначала проверь, что путь не пересекается с `/api/`.
- **`components/ServiceWorkerRegister.tsx`** — регистрирует SW, только в
  проде (`NODE_ENV === 'production'`), чтобы не мешать HMR в разработке.
- **`components/InstallPwaButton.tsx`** — явная кнопка «📲 Установить
  приложение» (не текстовая ссылка), внизу страницы перед футером — и на
  лендинге, и в личном кабинете (`DashboardShell`, видна на всех вкладках).
  Определяет iOS/Android через `navigator` и показывает разную инструкцию:
  у iOS нет `beforeinstallprompt` вообще (только Safari → «Поделиться» →
  «На экран Домой»), у Android событие `beforeinstallprompt`
  перехватывается и даёт нативную кнопку установки.
- **Push-уведомления (Web Push + VAPID)**:
  - `lib/webPush.ts` — обёртка над `web-push`, `sendPushToUser(userId,
    payload, target?)` / `sendPushToAll(payload, target?)`, оба
    принимают опциональный `target: 'parent' | 'child'` для фильтрации по
    `device_type`. Истёкшие подписки (404/410 от push-сервиса) удаляются
    автоматически.
  - `push_subscriptions` в схеме БД, `/api/push/subscribe` и
    `/api/push/unsubscribe` — привязаны к обычной пользовательской сессии
    (Яндекс ID), не к админке.
  - `lib/usePushSubscription.ts` — общий клиентский хук (`status`,
    `loading`, `subscribe`, `unsubscribe`), один экземпляр создаётся в
    `DashboardShell.tsx` и пробрасывается пропсами в
    `components/PushSubscribeButton.tsx` (кнопка «Включить уведомления»
    во вкладке «Настройка уведомлений») и `components/IosPushPrompt.tsx`
    — чтобы оба места не расходились в статусе, если пользователь
    подписался через одно из них, а не другое.
  - **Подписка запрашивается автоматически при каждом заходе в личный
    кабинет**, без клика по кнопке (`usePushSubscription(true)` —
    компонент, где вызывается хук, смонтирован всегда, все 4 вкладки
    `DashboardShell` в DOM одновременно) — осознанное решение владельца
    проекта, несмотря на то, что `Notification.requestPermission()` без
    явного жеста пользователя на **iOS Safari системный диалог вообще не
    показывает** (WebKit это блокирует). Если разрешение уже `denied` —
    повторно не дёргаем (`Notification.permission !== 'denied'`).
  - **`components/IosPushPrompt.tsx`** — компенсирует то, что не работает
    у автоподписки на iOS: свой попап с кнопкой «Разрешить», клик по
    которой и есть тот самый жест, которого требует WebKit. Показывается,
    только если: `detectPlatform()==='ios'` **и** `isStandalone()`
    (см. `lib/platform.ts`, общий с `InstallPwaButton.tsx`) — в обычной
    вкладке Safari (не установлено на главный экран) просить разрешение
    бессмысленно, пуш там всё равно не покажется (см. ловушку iOS ниже).
    Отказ («Не сейчас») запоминается в `localStorage`
    (`ios-push-prompt-dismissed`) — не показываем повторно каждый визит;
    вручную включить уведомления всегда можно во вкладке «Настройка
    уведомлений».
  - **Триггеры отправки:**
    - Ручной, из админки (`components/AdminPushBroadcast.tsx` →
      `/api/admin/push-broadcast`, рассылка всем/родителям/детям).
    - Проверка готова → устройствам с `device_type='parent'`
      (`app/api/checks/route.ts`, после успешной вставки в `checks`,
      **await**, не fire-and-forget — serverless-функция может быть убита
      сразу после ответа). Пуш ведёт на `/dashboard?tab=history&checkId=...`
      — `HistoryTab.tsx` читает `initialExpandedId` и сразу раскрывает
      нужную карточку; `public/sw.js` (`notificationclick`) находит уже
      открытое окно дашборда по pathname и делает `client.navigate()` на
      точный URL с query, а не просто фокусирует его.
    - Напоминание «пора делать уроки» → устройствам с `device_type='child'`
      по расписанию, которое задаёт родитель (см. ниже).
  - **Тексты автоматических триггеров редактируются из админки**
    (`components/AdminPushTemplates.tsx` → `GET`/`PUT`/`DELETE`
    `/api/admin/push-templates` → таблица `push_templates`, ключи
    `check_ready`/`reminder`). Пока текст не переопределён — используется
    дефолт из `lib/pushTemplates.ts` (`PUSH_TEMPLATE_DEFAULTS`), поведение
    не меняется, пока админ ничего не настроил. `check_ready` поддерживает
    плейсхолдеры `{subject}`/`{grade}` в теле (`renderTemplate()`);
    `app/api/checks/route.ts` и `app/api/cron/reminders/route.ts` берут
    текст через `getPushTemplate(key)` вместо хардкода. Не путать с
    `AdminPushBroadcast.tsx` (`/api/admin/push-broadcast`) — там текст
    вводится вручную при каждой разовой рассылке, это про другое.
  - **Метки устройств «родитель»/«ребёнок».** Один аккаунт (один
    Яндекс ID) может быть установлен на нескольких устройствах — типичный
    случай: у родителя и у ребёнка. Каждая push-подписка хранит
    `device_type` (`parent`/`child`, nullable) и `device_label`
    (произвольное название). **Первое устройство, которое пользователь
    когда-либо подписывает на аккаунте, автоматически становится
    `device_type='parent'`** (`app/api/push/subscribe/route.ts` — считает
    существующие подписки пользователя перед upsert; если их 0, добавляет
    `device_type: 'parent'` в payload). Все следующие устройства остаются
    неразмеченными — родитель размечает их (обычно как «ребёнок») вручную
    в личном кабинете (`components/PushDevicesManager.tsx` →
    `GET`/`PATCH` `/api/push/devices`). Это правило применяется только к
    новым подпискам — под уже существующие аккаунты задним числом не
    подставляется (сознательное решение, не забыть, если понадобится
    миграция).
  - **Дедупликация устройств по `client_device_id`.** Web Push `endpoint`
    может смениться на том же физическом телефоне (переподписка, сброс
    разрешений в настройках ОС, особенности iOS) — раньше это создавало
    отдельную "устройство-призрак" запись при каждой такой смене, и
    "Устройства для уведомлений" заполнялись дублями одного и того же
    телефона (реальный кейс в проде). Теперь `lib/usePushSubscription.ts`
    генерирует случайный `client_device_id` при первой подписке и хранит
    его в `localStorage` (переживает переподписку) — при каждом
    `POST /api/push/subscribe` сервер ищет старые записи с тем же
    `client_device_id`, но другим `endpoint`, переносит их
    `device_type`/`device_label` на новую запись и удаляет старые. Работает
    только для новых подписок — уже существующие дубли (у которых
    `client_device_id` ещё `null`) не сливаются автоматически, их нужно
    убрать вручную кнопкой «🗑 Удалить» у каждой лишней записи
    (`DELETE /api/push/devices`, добавлено вместе с этим фиксом).
  - **Напоминание о домашке** (`components/ReminderSettings.tsx` во
    вкладке «Настройка уведомлений» → `GET`/`PUT` `/api/reminders` →
    таблица `reminder_settings`). Родитель включает тумблер, отмечает
    будние дни (Пн–Пт) и одно время — одна настройка на весь аккаунт (по
    ребёнку отдельно пока нельзя, раздел «Дети» не реализован).
    `app/api/cron/reminders/route.ts` — публичный (но защищённый секретом)
    эндпоинт, который на каждый вызов: считает текущее время/день недели
    в Europe/Moscow, находит включённые расписания на сегодняшний будний
    день, у которых `last_sent_date` ещё не сегодня и целевое время уже
    наступило (окно допуска `TOLERANCE_MINUTES = 9`, чтобы не потерять
    напоминание из-за дребезга внешнего таймера), шлёт пуш `device_type='child'`
    и проставляет `last_sent_date`. `PUT /api/reminders` **обнуляет
    `last_sent_date`** при каждом сохранении настроек — иначе правка
    времени/дней в тот же день, когда напоминание уже сработало (даже по
    старым, ещё не изменённым настройкам), навсегда блокирует повторную
    отправку до завтра, а `/api/cron/reminders` молча возвращает
    `checked:0` без единой ошибки (реальный кейс в проде — нашли только
    через `select * from reminder_settings` и `net._http_response`, не
    забыть эти два запроса при следующей похожей жалобе). **Это НЕ Vercel
    Cron** — на бесплатном
    (Hobby) тарифе крон запускается не чаще раза в день, чего недостаточно
    для точного времени. Вместо этого эндпоинт дёргает **сам Supabase** —
    `supabase/cron.sql` включает расширения `pg_cron` + `pg_net` и заводит
    задачу, которая раз в минуту делает `net.http_get()` на
    `GET /api/cron/reminders?secret=$CRON_SECRET` (секрет можно передать и
    как `Authorization: Bearer $CRON_SECRET`, если понадобится другой
    способ вызова). Выбрано вместо внешнего пинг-сервиса (cron-job.org и
    т.п.), чтобы не заводить лишнюю стороннюю зависимость — Supabase уже
    используется как основная БД, `pg_cron`/`pg_net` доступны на любом
    тарифе. `supabase/cron.sql` нужно выполнить один раз вручную в SQL
    Editor (с реальным доменом и секретом вместо плейсхолдеров в файле) —
    сам по себе эндпоинт ничего не вызывает по расписанию.
  - **Известная ловушка iOS: пуш «отправлен», но не приходит.** Если
    пользователь разрешил уведомления и подписался, находясь в **обычной
    вкладке Safari** (не в установленном на главный экран приложении),
    iOS молча принимает подписку и наш сервер честно получает от
    push-сервиса успех (`sent > 0`), но само уведомление физически
    никогда не показывается — это ограничение iOS (16.4+), не баг кода.
    Чинится так: установить сайт на главный экран («Установить
    приложение» → «Поделиться» → «На экран «Домой»»), открыть **именно
    со значка на главном экране**, там в «Настройка уведомлений» нажать
    «Отключить уведомления» → «Включить уведомления» ещё раз (создаёт
    новую подписку с новым endpoint — старая просто отвязывается от
    показа, permission-промпт при этом может не появиться повторно, если
    разрешение уже было выдано раньше, это нормально). Новое устройство
    при этом **не** получит `device_type='parent'` автоматически (см.
    выше — правило только для самого первого устройства на аккаунте),
    его нужно будет отметить вручную в «Устройства для уведомлений».
    После пересоздания подписки самый первый тестовый пуш может не
    дойти из-за небольшой задержки прогрева канала на стороне iOS —
    прежде чем считать проблему нерешённой, стоит подождать и
    попробовать ещё раз — в первом реальном случае с этой проблемой
    помогло само, без дополнительных действий, через какое-то время
    после пересоздания подписки.
  - Нужны переменные окружения `NEXT_PUBLIC_VAPID_PUBLIC_KEY` +
    `VAPID_PRIVATE_KEY` (одна пара, сгенерировать: `npx web-push
    generate-vapid-keys`) и `CRON_SECRET` (любая случайная строка — для
    защиты `/api/cron/reminders` от произвольных вызовов). `NEXT_PUBLIC_...`
    встраивается в клиентский бандл **на этапе сборки** — если меняешь
    ключ, нужен новый деплой, просто поменять переменную в Vercel без
    пересборки не сработает.
